\section{Experimental Setup}
\label{sec:experimental_setup}

The benchmark was conducted on a controlled hardware and software environment to ensure deterministic execution. The experiments were run on macOS 14.0 (Darwin 23.0.0, Apple M2 ARM64 architecture) using Python 3.13.7. 
The evaluated engines included PySAT Glucose3, OR-Tools CP-SAT (version 9.15.6755), Gurobi Optimizer (version 13.0.3), and IBM ILOG CPLEX / CP Optimizer (version 22.2.0.0).

We evaluated 9 distinct solving methods across 11 instance sizes: $N \in \{4, 8, 16, 20, 31, 32, 40, 44, 50, 64, 100\}$. Each configuration was repeated 5 times, yielding 495 planned official trials.
To guarantee fairness, every trial was executed in an isolated subprocess. All methods were configured for single-threaded execution (\texttt{workers=1}). For exact baseline solvers exposing random seed and native timeout APIs (Gurobi, CPLEX, CP-SAT), parameters were explicitly set to \texttt{random\_seed=0} and a 300.0-second internal limit. For Boolean SAT models solved via PySAT Glucose3, the engine does not expose native wall-clock or random seed parameters in this interface; thus, Glucose3 ran under its default deterministic heuristics, bounded by an external 330.0-second subprocess supervisor watchdog that forcefully terminated non-terminating executions.

The primary metric for comparative evaluation across methods is \textbf{pipeline total time}, capturing end-to-end execution (model construction, solver loading, search, and independent solution verification). In addition, fine-grained phases were instrumented: for SAT formulations, model creation time (\texttt{encoding\_time}), formula ingestion into the C++ solver core (\texttt{load\_time}), and CDCL search (\texttt{search\_time}) were logged separately, satisfying $\texttt{solve\_time} = \texttt{load\_time} + \texttt{search\_time}$. The 5 isolated repetitions per configuration measure deterministic runtime and environment variance under a fixed configuration.

Memory consumption was monitored as \textbf{sampled process-tree Resident Set Size (RSS) in MiB}, recorded by polling the root process and all recursive children at 0.1-second intervals via \texttt{psutil}. Two experimental caveats apply to this metric: periodic sampling may miss transient peak allocations occurring strictly between 0.1s intervals, and summing RSS across parent and child processes may double-count physical pages shared via copy-on-write fork semantics or dynamic system libraries. Runs blocked by proactive Community Edition license constraints (\texttt{BLOCKED\_LICENSE}) were explicitly flagged to distinguish commercial capacity boundaries from algorithmic intractability.
